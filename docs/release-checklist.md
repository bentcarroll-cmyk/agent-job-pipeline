# Local release checks

Development history may contain private assumptions. Never push development history. The public Git root must be newly initialized from the explicit `.release/public-manifest.json` allowlist. Copy only reviewed regular files from the selected immutable development commit, with an external path/hash receipt. Include hidden assistant adapters, native `.mjs`/`.d.mts` tools, tests, schemas and CI. Exclude local workspaces, source import receipts, SDD records, operational snapshots, resumes, mail, PDFs and fonts.

Run Node 22 checks with locked npm dependencies. Run the Python 3.12 material suite separately with the macOS-scoped fully pinned requirements lock. Python package versions are pinned, not wheel hashes. Complete two fabricated journeys with actual local D1 and PDFs and fabricated providers. The materials suite checks default macOS Arial; set `MATERIALS_TEST_FONT_DIR` to a reviewed installed Liberation Sans directory to run every explicit fallback test. Render and visually inspect every resulting PDF page. No other installation platform is advertised.

1. Run `npm run verify`, `npm run guides:check`, and the Python suite. The full journey uses `MATERIALS_PYTHON` or `tools/materials/.venv/bin/python`.
2. Create the separate public root from the final allowlist, initialize new history with the intended public author identity, commit its exact tree, and record its SHA. Do not add a development remote/history.
3. Run `npm run privacy:check -- --root /absolute/public/root --history`. This scans its entire tracked worktree and every reachable commit's file content and metadata. Findings contain locations and rule names only. Review the exact public root and assets independently; heuristic scanning cannot prove absence of all private information.
4. Run `npm run package:release -- /absolute/public/root /absolute/release-output`, then `npm run release:verify -- /absolute/release-output/agent-job-pipeline.tar.gz`. Build twice into distinct output directories and compare SHA-256. Inspect archive member names and its content hash manifest. Strict verification rejects traversal, duplicate paths, symlinks, missing required tooling, hash mismatch and private assets.

A passing archive is an integrity receipt, not publication approval. Local green checks do not imply hosted CI or actual assistant/account acceptance. Use a fresh Slack app with an unused `/job` namespace, or another Slack workspace when an active app owns that command.

## Final candidate and publication gates

The final allowlist now includes LICENSE, installation results, release notes and the release tool. Its stage is `candidate`; packaging alone does not approve release. The beta package version is `0.1.0-beta.1` and its tag is `v0.1.0-beta.1`. Deliberately select `--channel beta`; the default stable channel requires package version `0.1.0` and tag `v0.1.0`. Channel and version are immutable candidate fields checked against the committed package. No failing stable candidate automatically becomes a beta.

After the initial clean public root is committed on main, create an external evidence JSON with `schemaVersion:1` and one `checks` entry for each of: `local-verification`, `materials-and-visual-review`, `codex-installation`, `claude-installation`, `bounded-live-discovery`, `signed-slack-callbacks`, `gmail-readonly-recovery`, `test-resource-cleanup`, `hosted-ci`. Each entry contains `name`, `status` (`passed`, `pending` or `failed`), the exact `candidateSha`, and `evidenceSha256` (a SHA-256 of the sanitized supporting receipt, or null for an unobserved check). A passed check requires a real evidence hash; the tool validates structure and bindings, while independent reviewers validate the evidence's meaning. Never promote a synthetic or partial check to passed.

Run from a reviewed tool installation, with the exact clean root and an existing external parent directory:

```sh
npm run release -- prepare --root /absolute/public/root --output /absolute/new-candidate-output --evidence /absolute/private/checks.json --channel beta
```

`prepare` requires a fresh output directory and creates the reproducible archive, checksum and `candidate.json`. Pending checks are allowed in a review candidate. It never writes approval. Its record binds repository/channel/version, root and linear lineage hashes, predecessor receipt hash, current SHA/tree, manifest/archive, license/results/notes and the sole advertised platform `macos-arm64`. Outputs stay outside the source root.

After independent code/candidate review and local checks, the controller may create only the new private destination repository and push only this reviewed clean-public main to run hosted CI. No development remote, old refs, `--all`, tag, release or visibility change belongs in staging. Keep every staged commit immutable. If hosted CI or acceptance exposes a source defect, append a correction on this same clean-public main, copying only reviewed selected files from committed development blobs and updating the explicit manifest. Never merge or fetch private development ancestry. Every historical tree must match its own committed manifest with regular files only; all reachable content and metadata are scanned. Preparation refuses non-linear or shallow history and extra local refs. The sole permitted tracking ref is `refs/remotes/origin/main`, which must belong to that same clean-public lineage; for a revision it must name the reviewed immediate predecessor or the current candidate already staged.

Prepare corrected candidate B with `--previous-candidate /absolute/A/candidate.json --previous-approval /absolute/private/A-review.json`, plus the same explicit channel, fresh B-bound evidence and a fresh output directory. A reviewed lineage retains its channel and version. The prior receipt must bind the immediate parent A and its clean-public root/lineage, with independent approval of those exact receipt bytes. This staging review can record pending full acceptance; it cannot authorize publication. B requires its own independent review before a normal fast-forward push of main to the same private destination. Verify the destination still contains only the expected reviewed A main before pushing; an unexpected ref/state is a stop, never grounds for force-push, reset, deletion or adoption. Run and observe new hosted CI at B. Old A evidence or approval does not approve B.

External current acceptance receipts may be updated for an unchanged SHA with a newly prepared record and renewed review. Source-affecting fixes to CI, installation instructions, tests, runtime or committed results require a descendant commit and the same B procedure. Installation results in source are a historical snapshot; current acceptance is established only by exact-SHA external receipts.

Stable publication requires all nine checks passed. Beta publication requires `local-verification`, `materials-and-visual-review` and `hosted-ci` passed; unobserved native/live/cleanup checks stay pending. Any known failed check blocks either channel. A beta does not certify hosted installation.

After the selected channel's required actual checks pass, an independent reviewer creates an external approval JSON: `schemaVersion:1`, `approved:true`, `candidateReceiptSha256` containing SHA-256 of the exact candidate.json bytes, and `reviewedAt` containing an ISO timestamp. Approval is a trusted operator/reviewer artifact, not a cryptographic identity attestation. Review the actual files and supporting evidence before producing it. The preparation script must never approve itself.

```sh
npm run release -- publish --root /absolute/public/root --candidate /absolute/candidate-output/candidate.json --approval /absolute/private/independent-review.json
```

`publish` refuses moved or dirty candidates, invalid clean-public lineage, manifest/tree/archive drift, changed review records and any pending/failed required check. It additionally reads the selected private repository's exact main SHA, all remote references and current GitHub Actions check runs. Extra branches, tags, notes or stash refs are refused; only reviewed main and the tag created by this invocation may be present. Missing, pending, failed, stale or truncated hosted check results fail closed. The initial release inventory must be empty, including releases whose tags were deleted. It creates an exact lightweight tag and draft release only in that private staged repository, binds the returned draft ID, exact version/title, committed release-notes body and channel-specific prerelease state, and the exact two archive/checksum asset IDs, and downloads both assets to verify their exact bytes and digests. It rechecks the complete release and asset inventory immediately before changing visibility, before publishing the draft, and in final readback. Unexpected, duplicate, replaced or missing releases/assets stop publication; nothing is deleted or overwritten. Final readback also checks visibility and main/tag before writing an external publication receipt. Beta creation and publication explicitly set `prerelease=true` and `make_latest=false`, and every release metadata readback checks prerelease state. The [GitHub Releases API](https://docs.github.com/en/rest/releases/releases) defines these fields; prereleases cannot be latest releases.

If any remote mutation has an uncertain outcome, stop and reconcile exact remote refs, release and asset IDs. A retry refuses any existing release or additional ref; do not delete or overwrite them to bypass that stop. Public visibility cannot be transactionally coupled to publishing a release, so a failure between those operations requires explicit reconciliation. No path force-pushes or rewrites history.

The verification workflow runs on pushes to `main` and pull requests. Release-tag pushes do not start a duplicate check at an already reviewed source commit; the exact main-commit hosted check is still mandatory before publication. See [GitHub push event filters](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push).
