# Private, recoverable setup (macOS)

Use a separately selected private workspace outside both the release checkout and any protected source checkout. The commands require absolute `--workspace` and `--instance` paths; the instance file must resolve inside that workspace, including through symlinks. Put your approved `candidate.json` and the actual approved UTF-8 `criteria.md` there. Setup checks the readable file's bytes and both candidate approval hashes. It never creates or repairs approval hashes.

Use [core-only private dependency bootstrap](../SETUP.md) first on a clean checkout. Run with its absolute private tsx loader, Node 22 and an explicitly selected Python 3.12 executable:

```sh
node --import /absolute/private/workspace/.setup/dependencies/node_modules/tsx/dist/loader.mjs tools/setup/cli.ts check --workspace /absolute/private/workspace --instance /absolute/private/workspace/instance.json --python /absolute/python3.12
node --import /absolute/private/workspace/.setup/dependencies/node_modules/tsx/dist/loader.mjs tools/setup/cli.ts status --workspace /absolute/private/workspace --instance /absolute/private/workspace/instance.json
```

`check` creates locked Node dependencies and an isolated Python environment under `.setup`, checks dependency consistency, embeds the macOS Arial font in a synthetic PDF, extracts text and rasterizes it. It neither installs global packages nor changes global settings. Unsupported runtime/platform/document capabilities stop setup. Resumes reverify the lock and private Python/document capability. Candidate bindings are limited to 5 KiB UTF-8; larger profiles are losslessly gzip/base64 encoded, with a 256 KiB decoded limit. Profiles too large for either limit stop without removing sources or policy fields.

## Resources and ownership

`resources` requires `--provider-writes approved` plus an explicitly supplied `CLOUDFLARE_API_TOKEN` for the selected account. Do this only when you intend account operations. There is no ambient Wrangler login discovery. The resource adapter uses Cloudflare's documented account APIs; Wrangler validates generated builds offline. No token is persisted, printed or passed in a command argument.

Before any create request, setup saves randomly generated 128-bit resource names and a creation intent under `.setup/resources.json`. Resources are not adopted by supplied names. An uncertain response is reconciled only against that exact prior intent, account, name and returned opaque ID; confirmed IDs are retained. A foreign collision, changed ID, missing confirmed resource or ambiguous match stops. If a pending creation cannot be found, setup stops with `RESOURCE_CREATION_UNCERTAIN`; establish provider truth before any manual repair. Never delete an intent to force a retry while a write may still be in flight.

Worker creation is metadata-only `POST /accounts/{account_id}/workers/workers` with public and preview subdomains disabled. It does not upload code or create a deployment. Locked Wrangler rejects `versions upload` for a nonexistent Worker, so setup does not pretend that upload creates the parent. Worker deployment/version upload and account acceptance remain explicit later operations. D1 and gateway create/read/list use native identifiers; D1 has no invented instance tag. Initialization writes a separate `setup_instance_identity` marker, verified before upgrades or activation.

Fresh databases receive the complete root schema and all represented migration IDs/hash receipts in one batch. They never replay the historical ALTER migrations. Upgrades require existing setup ownership and receipt provenance, apply only missing migrations, and commit each migration's DDL and receipt in the same transactional D1 batch. Lost responses are reconciled from committed receipts. Unknown databases or changed historical migration hashes stop; there is no inference from table presence or import of existing personal data. The metadata tables do not rewrite application records, run snapshots, leases or delivery receipts.

Primary provider references: [metadata-only Worker creation](https://developers.cloudflare.com/api/resources/workers/subresources/beta/subresources/workers/methods/create/), [D1 query batches](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/), [transactional D1 batch behavior](https://developers.cloudflare.com/d1/worker-api/d1-database/), [gateway creation](https://developers.cloudflare.com/api/resources/ai_gateway/methods/create/), [binding limits](https://developers.cloudflare.com/workers/platform/limits/).

## Preview and explicit activation

After resources are verified, `preview` validates the profile and generated bindings and runs two offline Wrangler dry-run builds. It records exactly those checks in `.setup/preview.json`. It does **not** claim live source/model/Slack/Gmail acceptance. Generated preview instances have `shadowMode=true` and radar disabled; operational HTTP, scheduled and Workflow entry points stop before ledger/provider work. Existing bounded discovery preview code in `src/discovery-preview.ts` remains available for a later explicitly authorized source-only guided preview; this CLI does not invoke it or imply it ran.

Validated instance fields control account/gateway, Slack channel and required authorized user, screening/manual screening mode, shadow and radar flags/budget/channel. Lifecycle enablement and start date come from the instance. Its separate explicit runtime mode can only narrow execution: `off` stays off; only literal `live` with enabled, non-shadow instance allows ledger mutation; all other values remain test mode. Operational generated bindings explicitly select live for enabled lifecycle. Test-mode receipt promotion/reconciliation behavior remains covered by the lifecycle suite. Disabled radar does no work and requires no radar credentials. Enabled radar uses the admitted approved candidate, selected supported topic IDs and configured timezone; unknown topic IDs stop before provider calls.

Run `activate` with the selected workspace/instance and `--provider-writes approved` to produce a private `.setup/activation-review.json`. It records current active revision, exact resource IDs, instance hash, candidate hash and readable hash; its cutover fields start unapproved. Before submitting the review, externally suspend scheduled and manual delivery, drain running Workflows, and reconcile uncertain Slack requests. Set `externalQuiesced`, `receiptsReconciled`, a concrete evidence note, and current `reviewedAt`. Then rerun with `--review /absolute/private/workspace/.setup/activation-review.json`.

Activation revalidates ownership, actual approval bytes, the reviewed instance and resource IDs, the matching offline preview receipt, active leases and unresolved delivery attempts. It uses the independent active-config D1 compare-and-swap API; stale revision approval fails. A persisted intent allows only exact revision+1/hash reconciliation after a lost response. It never silently adopts a newer revision or reapproves a changed profile. D1 and Slack do not share a transaction: operator-confirmed external suspension/drain is a required gate, not an inferred guarantee from zero D1 rows. An already-started Slack request cannot be recalled.

Activation emits operational configs after reviewed quiescence and D1 CAS but does not deploy them. Preview and shadow configs include explicit `crons=[]`; reviewed operational configs contain one `*/5 * * * *` UTC dispatcher per Worker. Omitting triggers would preserve old schedules on redeploy, so omission is not used. The two emitted ticks consume account cron capacity; available quota and live activation require separate account/deployment checks. Credentials remain separate redacted actions; the Gmail auth helper is documented in `lifecycle-setup.md` and must be invoked separately after verified resources and consent.

## Recovery and privacy

All generated config, dependency installs, state, review and migration intent files belong under the selected workspace's private `.setup` directory. Receipts are atomically replaced, fsynced and mode 0600; the directory is mode 0700. A per-workspace exclusive lock covers CLI operations. `SETUP_LOCKED` does not automatically steal a lock based on age or PID. After a crash, verify the recorded process has stopped before explicitly removing only `.setup/lock`; retain all receipts and intents. A new invocation then rechecks current evidence and provider truth.

Do not copy another person's workspace, resource receipt, approvals or credentials. Fresh installation requires fresh resource names/IDs; migration of an existing live personal deployment is a separate project. Current verification is offline/synthetic/local D1 only. No live deployment, authentication, secret upload, scheduled run or provider acceptance is claimed by this setup implementation.

Setup preserves the existing `HOME` in every subprocess. npm uses private user/global/project config and cache; pip disables ambient configuration and uses a private cache. The Python environment uses copied executables. Existing setup paths are checked before writes and subprocesses: escaped links, special files and linked write destinations fail closed. Contained dependency executable links are supported. Recreate an old setup dependency environment if it contains executables linked outside `.setup`.

Offline Wrangler builds use private XDG config/cache, explicit log/cache paths and an empty env file. No login is discovered: a deliberately invalid offline-only token prevents stored credential lookup. Wrangler 4.135 still prefers an existing `~/.wrangler` over XDG and accesses telemetry metadata even when metrics are disabled. Setup checks only that directory entry and stops with `AMBIENT_WRANGLER_CONFIG_UNISOLATED` if it exists; it does not read or move its contents or change `HOME`. A future Wrangler version with a verified explicit global-config override is required to support that host layout safely.

Before any provider action, setup checks both preview and operational instance bindings using the persisted generated resource names and a full schema-bounded D1 UUID. Oversized fresh or resumed plans stop with `INSTANCE_BINDING_TOO_LARGE` before creating resources.

## Timezone scheduling

Set an explicit IANA timezone and 24-hour local times at five-minute granularity (`09:00`, `09:05`, etc.). Invalid zones or off-grid times stop configuration admission and activation. Discovery follows the selected ISO weekdays (1 Monday through 7 Sunday); lifecycle and radar follow daily local times, with their instance feature flags checked before dispatch. An explicit lifecycle runtime `off` also suppresses scheduled lifecycle work.

Both generated Workers receive the same UTC tick. The fixed Worker owns fixed-board discovery; the unbounded Worker owns open discovery, lifecycle, radar and manual intake recovery. Discovery fans out with distinct Workflow IDs. Calendar IDs prepend the complete instance ID, workflow identity and local date/time; repeated delivery and both occurrences of a fall-back hour share one intended slot. A local time skipped during spring-forward is skipped for that date, without catch-up. UTC cron text is the dispatcher frequency, not a conversion of user-local times.

Intake recovery runs every UTC five-minute tick, including both fall-back occurrences, and retains its existing request/generation IDs, retry state and leases. Calendar deduplication does not gate recovery. Workflow names are checked against the provider's 64-character limit before resource operations/rendering; scheduled instance IDs stay within 100 characters with provider-safe characters even at the maximum 63-character instance prefix. These are offline configuration guarantees, not live account quota or deployment acceptance.

## Clean dependency bootstrap and bundling

The Node-core `tools/setup/bootstrap.mjs` shares the exact workspace/path/tree/lock/atomic-write guards with the TypeScript setup facade. It installs only the reviewed lock under the selected private `.setup/dependencies`; no checkout-local `node_modules` is required. Invoke the CLI using the returned absolute private tsx loader as shown in [SETUP.md](../SETUP.md). Dependency rechecks compare the selected lock to the reviewed release and run npm consistency checks before preview/activation.

Offline builds use that workspace's private Wrangler. Generated unbounded configs contain a guarded absolute alias to the selected locked Anthropic SDK entry; it is a local bundling path, not part of candidate/instance configuration. This uses Wrangler's documented [alias resolution](https://developers.cloudflare.com/workers/wrangler/configuration/#bundling-issues). Source files remain in the release checkout; setup does not copy a second source tree or use global dependency resolution. Both preview and operational emission use the same selected private alias.

The Python material environment uses `tools/materials/requirements-macos-py312.lock`: all 15 direct/transitive package versions are pinned, with no wheel hash enforcement. This lock was installed and checked on macOS arm64 with Python 3.12.14. `requirements.txt` retains the four direct dependency intentions. Installation support for other platforms requires separate verification.
